# 幂等键工程形态设计（clinic-14）

## 一、问题口径

访视批次「追加抓取」缺少请求级幂等键：同批数据重试/重复提交时，只靠
`visit_rows` 的业务唯一键 `(batch_id, subject_key, visit_code)` 兜底，
表现为要么报错、要么在并发争用下重复灌行，质控与补采数字随之虚高。

本题只盯幂等键：幂等键必须入表（有落点行）、当场铆死、钤印防篡改、
提交即刻落定、整笔失败可回滚、争用不加锁不得双成功。

## 二、甲乙两轨骨架（先备齐，编译只留已选边）

### 甲路 · 旁路账册（写侧）—— 本题已选边，端到端接线

- 新建旁路账册表 `idempotency_ledger`，与业务表 `visit_rows` 分离。
- 追加访视行时，先把幂等键作为账册**当场唯一键**铆死
  （`idem_key TEXT UNIQUE` + `BEGIN IMMEDIATE` 写锁 + UNIQUE 约束双保险）。
- 同时**钤印**：`stamp = sha256(口径域|批次|受试者|访视|幂等键)`，
  重复提交重算戳记与库存比对，拧花即拒（HTTP 409）。
- 读轨只认本账册：是否重放、追加次数、状态旗一律查 ledger，
  不回刷业务表反推。
- 挡掉回刷：同键再次提交不新增访视行、不改首笔结果，
  仅 `attempt_count + 1` 并原样回放首笔结果（`replay=True`）。
- 甲边封存收口：写侧逻辑定稿后不再扩张，只做归档收口。

### 乙路 · 只读归档（读侧）—— 甲路封存后的收口段，不另立并行读轨

- 过期档（关联批次已关闭）迁入只读归档表 `idempotency_archive`。
- 账册原档置新旗 `status_flag='已归档'`，现行读轨只认 `'现行'` 旗。
- 读侧分叉：现行队列读 ledger 新旗；归档页签只读 archive 表。
- 归档后同键再追加一律拒绝。

> 择边约束：访视批次列表、详情、队列的幂等读引用**唯一**指向甲路账册
> 现行旗；乙路仅在显式「归档收口」动作时运行，不存在两套并行读引用，
> 故无闲置旁路骨架。

## 三、幂等键口径（台参数页只展此项）

- 业务幂等键口径：`批次ID:受试者键:访视编码`（客户端未显式提交时按此确定性生成）。
- 请求幂等键：客户端可显式提交 `Idempotency-Key`，格式 `^[A-Za-z0-9:_-]{8,128}$`。
- 钤印算法：`sha256(scope|batch_id|subject_key|visit_code|idem_key)` 十六进制摘要。
- 状态旗：`现行` / `已归档`。
- 重复处置：同键重放挡回刷，首笔结果原样返回；戳记不符按拧花拒绝。
- 台参数新增只读口径项 `idempotency_key_spec`。

## 四、落点与表结构

- `idempotency_ledger`：幂等键当场铆死的账册（含 row_id 落点、戳记、状态旗、追加次数）。
- `idempotency_archive`：过期档只读归档。
- 历史 `visit_rows` 在迁移时按口径补植账册落点，保证种子批次徽标同样亮起。
- 每次追加成功，ledger 必有且仅有一条落点行指向新访视行。

## 五、败测清单（动笔改码前写定，先红后绿）

1. 追加成功 → 账册必有落点行，row_id 指向新访视行，戳记可重算核对。
2. 同幂等键重复追加 → 不新增行、批次行数不增、回放首笔结果、attempt_count=2。
3. 两侧并发争用同键（均不显式加锁）→ 恰好一行落库，一方重放/被拒，不得双成功。
4. 同键携带不同口径要素（戳记拧花）→ 409 拒绝，不放行、不新增行。
5. 整笔写库失败 → 账册与业务表双双无残留，错误信息明确讲明白。
6. 归档收口 → 档位置已归档旗、归档表有只读副本、现行队列读不到、同键再追加被拒。
7. 批次列表携带幂等徽标与追加次数聚合，且与账册一致（含挡回刷次数）。
8. 非法请求键格式拒绝；留空时服务端按口径生成确定性键。
9. 服务端自动键对同业务键第二次提交同样命中重放。
10. 台参数暴露且仅暴露幂等键口径项 `idempotency_key_spec`。

## 六、收工判据

- 缺落点而重复追加仍能成功 → 驳回。
- 徽标独亮但账册无落点行 → 驳回。
- 戳记拧花仍放行 → 驳回。
- 存在闲置未接线的旁路骨架 → 驳回。
